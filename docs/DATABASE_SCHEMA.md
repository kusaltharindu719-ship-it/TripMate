# TripMate – Master Database Schema

## 1. Purpose

This document defines the master database architecture for the TripMate web application.

The database is designed to support:

- Travelers
- Restaurant Owners
- Accommodation Owners
- Drivers
- Administrators
- Trip Planning
- Destinations
- Restaurants and Menus
- Accommodation and Rooms
- Attractions and Activities
- Trip Cart
- Driver Bidding
- Booking Management
- Reviews
- Notifications
- Maps and Location Services
- AI-Assisted Trip Planning

The schema should be reviewed before new database tables are implemented.

---

# 2. Database Technology

Database:

PostgreSQL through Supabase

Authentication:

Supabase Auth

Primary user identifier:

UUID

Most normal application records:

BIGINT identity primary keys

---

# 3. General Database Rules

## User IDs

User-related tables use:

uuid

because Supabase Authentication uses UUID values.

Example:

auth.users.id
↓
profiles.id

---

## Normal Record IDs

Normal system tables use:

bigint generated by default as identity

Example:

Restaurant ID
Trip ID
Room ID
Food Item ID

---

## Money

Money values use:

numeric(12,2)

Example:

12500.00

Current default currency:

LKR

Where required, a currency field may also be stored.

---

## Location

Location-based services use:

latitude numeric(9,6)
longitude numeric(9,6)

---

## Date and Time

Date only:

date

Time only:

time

Full timestamp:

timestamptz

---

## Status Fields

Status values are stored using text with CHECK constraints.

This makes the database easier to modify during development than fixed PostgreSQL enum types.

Managed automatically by Supabase Authentication.

Application code should not directly manage passwords.

# 5.2 profiles

Purpose:

Stores TripMate-specific user information.

Fields:

id uuid PRIMARY KEY
full_name text
phone text
role text
created_at timestamptz

Foreign Key:

profiles.id
→ auth.users.id

Delete Rule:

ON DELETE CASCADE

Allowed roles:

traveler
restaurant_owner
accommodation_owner
driver
admin

Current system rule:

One account has one primary system role.

Multi-role accounts can be added later if required.

# 18. Security and RLS Strategy

Row Level Security should be enabled on user-controlled tables.

General ownership rules:

Traveler:

Can read and update own profile.

Can manage only own trips.

Can manage only own trip cart.

Can view bids for own trip requests.

Can accept bids only for own trips.

Restaurant Owner:

Can manage only restaurants owned by their profile.

Can manage only menu items belonging to their restaurants.

Accommodation Owner:

Can manage only properties owned by their profile.

Can manage only rooms and offers belonging to those properties.

Driver:

Can manage only own driver profile and vehicles.

Can create bids using only own approved driver account and own vehicle.

Admin:

Administrative operations should be performed through secure admin authorization.

Sensitive backend keys must never be stored in frontend source code.

---

# 19. Important Data Integrity Rules

Foreign keys should be used wherever a real parent-child relationship exists.

ON DELETE CASCADE should only be used where child data has no meaning without its parent.

Historical booking data should not be deleted simply because a service changes later.

Prices should be copied into cart and booking snapshots.

Availability should be checked again when a booking is confirmed.

Driver bids should not remain valid forever.

Expired offers should not be treated as active.

A driver must not bid using another driver's vehicle.

A restaurant owner must not edit another restaurant.

An accommodation owner must not edit another property.

A traveler must not access another traveler's private trip.

# 25. Viva Explanation Principle

Every table must have a clear reason for existing.

For every database relationship, the team should be able to explain:

What the table stores.

Why the table is separate.

What its primary key is.

What its foreign keys are.

Whether the relationship is one-to-one, one-to-many, or many-to-many.

What happens when related data is deleted.

How unauthorized access is prevented.

Why a particular data type was selected.

How the table is used by the frontend and backend.

No database table should exist without an understandable purpose.
